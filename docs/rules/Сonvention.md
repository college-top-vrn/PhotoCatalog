## Создание ветки

В проекте используется методология **Git Flow** для упрощения совместной работы. Все стандартные ветки создаются от `develop` и используют строгие префиксы для категоризации.

### Основные типы веток:

* `feature/` — разработка новой функциональности (например, `feature/user-authentication`, `feature/login-page`).
* `improvement/` — улучшения, оптимизация и рефакторинг (например, `improvement/refactor-auth`).
* `test/` — ветка для написания автоматизированных тестов, создается строго от соответствующей ветки `feature/`.
* `bugfix/` — исправление ошибок и багов.
* `docs/` — обновление документации проекта.

### Порядок работы с тестами в Git Flow:

1. Создать ветку `test/` от вашей рабочей ветки `feature/`.
2. Написать в ветке `test/` все необходимые автоматизированные тесты.
3. Сделать `merge` ветки `test/` обратно в `feature/` только после того, как все тесты успешно пройдут локально.

### Приоритеты задач (Уровни P):

* **P0** — наивысший приоритет. Критически важные задачи, которые выполняются в самую первую очередь.
* **P1** — высокий приоритет, задачи выполняются сразу после P0.
* **P2** — средний приоритет.
* **P3** — низкий приоритет. Задачи для «свободного времени», выполняются в последнюю очередь.

## Создание Pull Requests (PR)

> **Перед созданием PR обязательно выполните команду `git pull origin develop`**, чтобы оперативно разрешить все возможные merge-конфликты на локальной машине.

### Принцип атомарности (Маленькие и направленные PR):

* Один PR должен решать строго **одну задачу**, содержать одну логическую фичу или один багфикс.
* Категорически запрещено смешивать в одном PR код дизайна, бизнес-логику, тесты и сквозной рефакторинг всего проекта.

### Требования к оформлению PR

**Заголовок:** Короткий, информативный, отражающий суть изменений.

* *Правильно:* «Добавлена проверка подлинности JWT для конечных точек API»
* *Правильно:* «Исправлено состояние гонки в очереди электронной почты»

**Описание:**

* **Цель изменения:** что именно делает этот PR и зачем это было нужно.
* **Влияние:** как код затрагивает пользователей, контракты, базу данных или миграции.
* **Связь с задачей:** ссылка на тикет или issue (например, `Closes #123`).

### Ревью и работа в команде:

* Обязательно назначайте **2 ревьюеров** в блоке *Reviewers*.
* Указывайте в качестве исполнителей (*Assignees*) всех участников команды, которые работали над этой задачей.
* Самостоятельный мерж PR запрещен политикой репозитория — необходимо получить одобрение (Approval) от ревьюера.
* Активно реагируйте на комментарии к коду: либо вносите правки, либо аргументированно объясняйте свою позицию в ветке обсуждения.

### Пост-мердж практики:

* Сразу после успешного мержа удалите временную ветку в удаленном репозитории.
* Обновите локальные ветки `main` и `develop` и убедитесь, что проект собирается и стабильно работает.

## Проектирование классов

Перед тем как приступать к написанию кода, исполнитель обязан спроектировать структуру будущих классов и сущностей.

### Требования к проектированию:

* Диаграммы строятся в формате **Mermaid**.
* На диаграмме обязательно должны быть отражены пространства имен (`namespace`).
* Необходимо явно указывать типы связей между классами (наследование, ассоциация, агрегация, композиция).
* Обязательно обозначайте модификаторы доступа (`+`, `-`, `#`) и модификаторы поведения членов класса.
* Готовый Mermaid-код сохраняется в отдельном файле Markdown (`.md`). Название файла должно четко отражать суть спроектированной системы.
* Файл схемы загружается строго в директорию: `docs/directories/`.

## Создание файлов и директорий

### Правила для директорий (папок):

* Имя папки пишется в стиле **PascalCase** (каждое слово с заглавной буквы, без пробелов и подчеркиваний).
* Название всегда пишется во **множественном числе** и четко отражает, какие объекты лежат внутри.

### Правила для файлов:

* Имя файла пишется в стиле **PascalCase**.
* Название файла должно полностью совпадать с именем класса или контракта, который в нем находится.

## Оформление XML-документации

* Тег `<summary>` запрещено писать в одну строку. Всегда разделяйте его на несколько строк для удобства чтения.
* Пишите документацию максимально подробно, описывая назначение методов, их параметры и возвращаемые значения.
* Соблюдайте единую терминологию проекта.

### Единая терминология:

* В текстах документации, комментариях и описаниях интерфейсы именуются исключительно как **контракты**.

## Правила принятия задания на изучение

1. Откройте рабочую доску и перейдите к колонке **«Материал для изучения»**.
2. Выберите нужную тему или документ и откройте его.

4. Переместите созданную подзадачу в колонку **«Изучаются»**.

## Правила автоматизированного тестирования

### 1. Требования к покрытию кода (Code Coverage)

* **Минимум 70%:** Любой написанный вами программный модуль (класс, сервис, логика) должен быть покрыт автотестами не менее чем на 70%.
* Если задача не имеет тестов или процент покрытия ниже нормы, она автоматически отклоняется на этапе Code Review и возвращается на доработку. Тесты должны проверять реальные кейсы и не должны быть искусственно завышены только ради метрик. Если тесты будут накручены ради покрытия, то исполнитель понесет наказание в виде сверхурочных работ и предоставления интимных услуг всей команде разработчиков

### 2. Стратегия тестирования и обязательные сценарии

Для каждого модуля пишется тестовый набор, который должен проверять код в четырех плоскостях:

* **Позитивные сценарии (Happy Path):** Проверяем, что код работает идеально и выдает правильный результат, если на вход пришли полностью корректные данные.
* **Негативные сценарии (Sad Path):** Проверяем поведение кода при передаче неверных данных, пустых строк или `null`. Код должен обрабатывать такие ситуации предсказуемо — возвращать специальный объект-результат (например, с флагом неудачи или списком ошибок валидации) или понятный код ответа, но приложение ни в коем случае не должно аварийно завершать работу.
* **Граничные значения (Edge-cases):** Проверяем работу на экстремальных границах (максимальные/минимальные значения чисел, пустые коллекции, строки нулевой длины, первый или последний элементы списка).
* **Тесты на крайние моменты:** Проверка поведения системы в специфических ситуациях взаимодействия внутренних элементов, когда проверяется комплексная работоспособность алгоритма под нестандартными условиями.

### 3. Юнит-тестирование (Unit Tests)

* **Цель:** Проверить работу одного конкретного класса в полной изоляции от остального мира.
* **Использование Моков (Mocks):** Если тестируемый класс использует базу данных, отправляет сообщения в очередь или делает запросы в сеть — в юнит-тестах эти зависимости **запрещено** делать реальными. Все внешние зависимости должны подменяться «пустышками» (моками) через их контракты (интерфейсы). Мы тестируем только чистую логику самого класса.

### 4. Интеграционное тестирование (Integration Tests)

* **Цель:** Проверить, как несколько написанных модулей работают в связке друг с другом и взаимодействуют с реальной инфраструктурой (базами данных, кэшем).
* **Правила написания интеграционных тестов:**
* **Независимость от локальной среды:** Тесты не должны ломаться из-за того, что у разработчика на компьютере не установлена конкретная база данных или утилита.
* **Изоляция и чистка данных:** Каждый тест обязан оставлять окружение чистым. Перед выполнением или сразу после него база данных должна возвращаться в исходное эталонное состояние (с помощью очищающих скриптов или отката транзакций), чтобы результаты одного теста не влияли на соседние.
* **Сквозные цепочки:** Тесты должны проверять полный путь прохождения данных: от вызова точки входа (Minimal API / Контроллер), через слои бизнес-логики и до фактического сохранения изменений в тестовой базе данных.

## Правила оформления тест-кейсов (Ручное тестирование)

*Примечание: данное оформление обязательно применяется при ручном тестировании бизнес-логики и тестировании WebApi (через Postman, Insomnia и аналогичные инструменты).*

### Каждый тест-кейс обязан содержать:

* **Заголовок:** Указание участников (кто тестировал, кто разработал) и точного объекта тестирования (метод, класс, контракт).
* **Описание:** Суть проверки и детальное описание ожидаемого результата.
* **Результат:** Четкий статус («Прошёл» / «Не Прошёл») и подробное текстовое описание фактического поведения системы.
* **Доказательства:** Ссылка на скриншот или лог, подтверждающий выполнение (снимок консоли, IDE или ответа в Postman).

### Правила хранения:

* Все файлы создаются внутри директории `test_case/`.
* Для каждого отдельного теста внутри `test_case/` создается своя папка с понятным названием. Внутри этой папки размещается markdown-файл с тест-кейсом (`.md`) и медиафайлы с доказательствами.

### Шаблон оформления тест-кейса:
Примечание: оформление надо делать при ручном тестирование и тестировании WebApi.

Каждый тест-кейс должен содержать::

- Заголовок: Укажите участников (тестировщик, разработчик) и тестируемый объект (метод, класс и т. д.).
- Описание: Что именно тестируется и ожидаемый результат.
- Результат: Явно укажите статус — "Прошёл" или "Не Прошёл" и написать сам результат.
- Доказательства: Прикрепите скриншот результата теста (консоль, IDE, Postman и т.д.).

Пример тест-кейса:

Тест-кейс: Иванов И.И. (тестер) + Петров П.П. (разработчик)
UserService.GetUserById(id: 123)

Ожидаемый результат: Возвращает User с ID=123 или null

СТАТУС: Прошёл

Результат: Вернул User с ID=123.

Дата: 17.04.2026

[Скриншот результата]

- Тест-кейс должен храниться в папке test_case.

- Структура должна быть такой: папка с названием теста, внутри — сам тест-кейс в формате .md и фото с результатом.
